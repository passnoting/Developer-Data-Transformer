5.4 AI 代码测试平台

一句话结论

需求是真的，但这是五个方向里最不适合 $0–100 预算的一个。不是因为没市场，而是因为它的商业模式需要“托管跑测试”——而你买不起那个算力，也不该替客户承担 CI 的可靠性。这个赛道刚刚用一家公司的死亡证明了这一点。

定价结构读出来的信息：这个品类已经分裂成两种完全不同的生意。一种是卖工具（Qodo、Coveralls、Codecov：$10–50/月，按席位或仓库），利润薄、增长靠 PLG；另一种是卖结果（QA Wolf、Momentic：$125–数千美元/月，按 run 或 credit），本质是“把 QA 外包给一个软件+人混合体”。后者的客单价是前者的 10–50 倍，但交付成本也高一个数量级——托管浏览器、维持测试稳定、处理 flaky。

用户差评：不是“不好用”，是“不敢信”

这个品类有一个别的品类没有的问题：AI 生成的测试会给你虚假的安全感。以下三条是 Hacker News 上的逐字原文，全部可点开核验：

“of the defects severe enough to warrant a formal RCA … 'AI generated tests asserted that the defective behavior was correct' was a contributing factor in every single one.” —— HN 用户 bunderbunder，2026-10-12。翻译：在那些严重到需要正式根因分析的事故里，“AI 生成的测试断言了错误行为是正确的”是每一起的促成因素。来源
“High coverage, confident test names, zero actual verification.” —— 高覆盖率、自信的测试名、零真实验证。来源
“AI-generated tests will often embed existing bugs as testable patterns… rely on empty asserts to increase coverage. Coverage is becoming theater.” —— 把现存 bug 固化成“预期行为”，用空断言刷覆盖率，覆盖率变成一场表演。来源
“Many of the passing tests it generated were tautologies… When the tests failed the agent tended to change the (previously correct) test.” —— 通过的测试是恒真式；一旦失败，agent 就去改那个（原本正确的）测试。来源
“The growth in brittle AI-generated tests means restructuring is more costly than it was before.” —— AI 生成的脆测试让重构变得比以前更贵。来源
“LLMs need a lot of cajoling to not build flaky tests… I spend hours rewriting parts of the test suite once or twice a week.” —— 不盯着就写 flaky 测试，每周要花几小时返工。来源

这不是个别吐槽，它和开发者调查对得上。Stack Overflow 2025 开发者调查（49,000+ 受访者）里：80% 已在使用 AI 工具，但对 AI 输出准确性的信任从 40% 降到 29%；66% 表示“几乎正确但不完全正确”的 AI 代码让他们花了更多时间修；45% 把“几乎对但不完全对”列为最大挫败。

这条差评的真正含义

用户不是想要“更多测试”，是想要“能信的测试”。而“可信”这件事无法用生成模型解决——它需要的是可执行的判定标准（这段代码的正确行为是什么）、变更影响面（改这行会破坏什么）、以及可复现（失败能不能稳定重现）。这三件事都不是“生成”，是“分析”。这就是缺口所在，也是一个人能做的部分。

缺口判断

三个候选缺口，按“一个人能不能做”排序：

  1. Flaky test 根因诊断（最可行）。输入：JUnit XML + 重跑历史；输出：“这个测试在 3 种条件下不稳定，根因是 X”。不需要托管 CI、不需要 GPU、不需要浏览器沙箱，只需要解析与统计。分发靠 CLI / VS Code 扩展 / GitHub Action。成本近乎为零，价格可以定 $19–49/月。劣势：市场天花板低（只有有 flaky 问题的团队才买），且“诊断”容易被 CI 厂商内置。
  2. 按变更风险排序补测试（可行但难卖）。纯静态分析 + 只跑受影响测试，技术上一个人能做，但“风险排序”的价值需要客户先有覆盖率数据，销售链条变长。
  3. Vibe coding 的验收测试（看着最热，实际最贵）。需要真浏览器沙箱、需要处理任意技术栈、需要替客户承担“测试挂了是不是你产品的问题”。$0 只能本地跑，托管必亏。
为什么这个方向不该是你的第一站
  • 买家是工程师，而工程师会自己做。你卖的每个功能，他们的第一反应是“这不就是个脚本”。付费意愿被“我能写”压制。
  • 信任门槛最高。测试工具的输出如果错了，客户会损失一次发布。这类产品的试用期长、决策慢、要求安全审查。
  • 交付成本不可控。托管跑测试意味着你要为客户的 flaky 买单；不托管则客单价上不去。
  • 刚刚死过一家。Octomind 的关闭说明“AI 生成 + 托管”的 PMF 不成立，而这个方向的最热叙事正是这个组合。

结论：如果你有 3–5 年测试/CI 经验，并且愿意做“诊断”而非“生成”，flaky 根因诊断是一个干净的切口，可以用 CLI + 内容站启动。但对“想拿第一批付费用户”的通用情形，它的获客速度和单价都不如第 3、第 5 个方向。
